# 整体业务向优化coding plan

- 日期：2026-10-10
- 依据：[整体业务向优化SDD](整体业务向优化SDD.md)，版本 0.1。
- 状态：实施计划；下列开发任务全部待执行，本文不代表代码、部署或验收已完成。
- 顺序：基线与合约 → S1 效果数据 → S2 内容生产 → S3 Agent 执行 → S4 分发策略 → S5 反馈学习 → 总体验收。
- 首个可交付版本：完成 CP00–CP06，得到可对账的曝光、点击、订单、花费与报表闭环。

## 1. 执行规则

1. 每次按一个任务推进；先核对该任务依赖、当前代码与 SDD，再改文件。
2. 每个任务交付业务逻辑、接口/迁移、必要验证和结果记录；验收通过后才能勾选完成。
3. 已有未提交改动不清理、不覆盖。复用广告事务、查单和托管运行能力，避免重写既有框架。
4. 新能力受阶段开关控制。只关闭新增入口，已接受事件、查单和回执继续处理。
5. 对账、权限、幂等、金额与版本正确性优先于吞吐；模型和外部 I/O 不进入业务数据库事务。
6. 方案变更先更新对应 SDD 条款，再调整本计划与验收用例；不通过改测试掩盖口径变化。
7. 每阶段更新实现说明与实际验证结果，不预写收益、P95 或容量成绩。

本计划不包含外部广告交易平台、真实资金结算、跨设备归因、生产反作弊、海量训练或亿级吞吐交付。

## 3. CP00：基线、共用文件和协议冻结

**目标：**保证后续开发使用当前实现和同一组业务口径。

实施步骤：

1. 记录当前 Git 状态、已有迁移、接口和测试结果；运行现有后端回归及前端构建。未配置服务导致的跳过单独记录。
2. 核对 `ads.model.ts`、`ads.database.ts`、`businessBoundary.ts`、`agent.routes.ts`、`hosting/api.py`、`hosting/pipeline.py`、`hosting/repository.py` 和助手组件。
3. 对照 [后端可靠性 SDD](backend-reliability-sdd.md)：复用它的有界广告上下文、共享对象存储、租约和 SSE 改造；业务计划不顺带实现多节点执行器修复。它规定的“本次不增加广告写工具”约束属于可靠性改造范围，业务 S3 按本 SDD 单独增加受控提案执行。
4. 确定营销 API 的 JSON 字段命名、错误结构、ID、整数金额、UTC 时间、环境、来源凭据和品牌归属合约；TypeScript 和 Python 共用版本化 JSON Schema/样例，分别做运行时校验。
5. 明确补充协议：展示凭证有效期与续发方式、自动重算窗口、退款先于支付的待处理状态、指标观察截止时间、接入来源完整性标记格式、策略随机种子、实验停止阈值。把决定同步写入 SDD，不能留到实现中各自猜测。
6. 引入五个阶段开关，默认关闭；校验依赖能力、迁移版本和阶段配置。过期提案、查单、回执及已接受事件不受入口关闭影响。

建议落点：`docs/marketing-api-contract.md`、`contracts/marketing/v1/`、Koa config/types、Python schema、`.env.example`、`docs/validation/marketing/`。这些是待新增位置。

验收：旧广告与聊天行为无回归；没有默认打开营销能力；字段和错误样例在两端校验一致；迁移编号与共用文件无冲突。首版事件等功能先在 synthetic 环境推进，无真实营销数据也可继续。

## 4. S1：效果数据闭环

### CP01：数据迁移、归属与最小资源

**目标：**每条新效果数据都能关联明确的活动、商品、素材版本与环境。

实施步骤：

1. 新增 `002_marketing_events.sql` 和独立营销迁移入口；记录版本/校验摘要，禁止修改 `001_ads.sql`。DDL 失败须明确报告，不宣称自动事务回滚；验证中途失败后可继续迁移。
2. 建立 S1 所需品牌、最小 membership、商品、Campaign、Creative、广告绑定、serving decision、event、attribution、ledger、coverage、daily metrics 和 outbox 表。
3. 品牌/商品初始记录通过幂等演示种子创建；S2 再扩展事实和创作者资料。最小归属检查从 S1 开始，完整创作者角色在 S2 开放。
4. 为 Campaign/Creative 增加状态、版本、起止时间、审核人和授权有效期；实现 SDD 的两个资源创建接口及旧广告绑定，资源读查询必须限于已授权品牌。
5. 对事件来源 ID、展示有效计数、订单当前归因、流水来源键增加数据库约束；原始事件可保留隔离记录，但有效计数约束独立定义。
6. 迁移旧广告只建立关联，保留原 price、clicks、version；不生成虚假的旧曝光和订单。复用现有 MySQL 连接池与有界等待，新增 Worker 单独核算连接预算。

改动位置：`apps/mini-ad-wall/server/migrations/`、`scripts/`、`services/marketing/resource.service.ts`、`models/marketing/`、`routes/marketing.routes.ts`；复用 `tests/helpers/mysql.cjs`。

验收：空库初始化、旧库升级、迁移重跑、中途失败续跑、跨品牌拒绝均可重复验证；数据库不可用返回 503；旧广告接口保持兼容。

### CP02：展示凭证、曝光和点击接入

**目标：**记录一次真实页面展示机会，重复上报不重复计数。

实施步骤：

1. 实现 `POST /serve`：只选择已关联、活动有效、审核通过且授权未过期素材；保存 decision 后返回短期签名凭证和 impression_id。S1 仍按旧规则排序。
2. 凭证绑定素材版本、Campaign、环境、匿名会话、目标链接和有效期；凭证签名参数由服务端控制。
3. 实现 `POST /events/impressions`：验证凭证，事务保存事件和 outbox；同时按来源事件键和 impression_id 处理重复、参数冲突。
4. 实现 `GET /click/:token`：同 impression 仅生成一次 click_id；重复访问复用 click_id 并跳转登记链接。落地页使用可验证关联凭证传递点击/会话，不接受伪造会话 ID 参与订单归因。
5. 前端曝光计时使用可见比例与页面可见性；达到 50% 且连续 1 秒才发送，重试保持事件标识；新页面停用旧 click 累加调用。
6. 覆盖素材重新渲染、标签页隐藏、点击先于曝光、凭证过期、跨素材串报和错误环境；新事件不写回 legacy clicks。

改动位置：营销 route、`serving.service.ts`、`event.service.ts`、`visitor-session.service.ts`、前端 `hooks/useAdImpression.ts` 与消费者展示组件。

验收：E01、E02；两个独立 Koa 进程同时上报，曝光和点击分别只记一次；凭证或事务失败不得返回接收成功。

### CP03：订单、退款、花费与完整性接入

**目标：**把订单和钱的来源固定下来，不依赖模型推测。

实施步骤：

1. 服务接入凭据绑定来源、环境、品牌及允许接口；浏览器不能以运营身份冒充订单/花费来源。
2. 实现 `POST /conversions`，支持支付和退款，时间/金额校验、支付订单去重、唯一退款事件及累计退款上限；对乱序退款按 CP00 协议处理。
3. 实现 `POST /spend-entries`，来源流水键唯一；同键同内容返回原结果，换金额返回 409；更正采用引用原记录的追加流水。
4. 实现 `POST /spend-coverage`，按区间数量、金额和摘要核对账本；来源未齐、流水更正或核对失败使完整性失效。
5. 接入成功写事件/流水和 outbox 同事务；不从浏览器接收可信 principal/source/environment。超出默认未来 5 分钟或延迟 30 天的数据进入隔离处理。
6. 建立服务端 synthetic 订单/花费生成器，覆盖正常、重复、缺来源、退款与错误金额。

改动位置：`conversion.service.ts`、`spend.service.ts`、`source-auth.ts`、`coverage.service.ts`、服务接入测试与种子脚本。

验收：E02、E05、E07 的接入部分；可信来源隔离、不同环境串报、重复退款与超额退款有确定结果；部分费用不能被标记为完整。

### CP04：异步归因、聚合与重建

**目标：**无论事件顺序和 Worker 重试如何，最终统计一致。

实施步骤：

1. 新建 `marketing/aggregation/`，通过 MySQL outbox 有界批次领取任务，保存租约/代次，事务外计算，提交时检查领取资格；任务状态与派生写入同事务完成。
2. 实现最后点击归因：同会话、同商品、同环境、支付前 7 天；同一时间按 click_id 稳定排序，无匹配记录明确原因。
3. 支付晚到、点击晚到、退款和更正按 received_at 找变化，再重算受影响订单与事件时间分区；归因 revision 替换当前指针，不新增一笔转化。
4. 分开维护按支付日的收入/订单和按点击日的 CVR 人群结果；无法从支付日聚合推导点击人群 CVR，使用可索引的 click-to-order 派生关联或独立聚合。
5. 重建任务显式指定环境、范围与规则版本；支持原始数据全量核对、日分区替换和 revision 保留。
6. 监测最老任务年龄、处理失败、隔离事件和积压上限；重试次数/截止时间有界，失败进入可追踪待处理状态。

改动位置：`marketing/aggregation/repository.py`、`worker.py`、`attribution.py`、`metrics.py`、`rebuild.py`；事件/outbox API 与专用 Worker 数据库权限。

验收：E04、E05、E07；独立进程在提交前后崩溃、租约过期与重放均不重复计数；顺序、乱序和重建结果精确一致。

### CP05：统一报表与证据快照

**目标：**页面和 Agent 使用完全相同的指标及口径。

实施步骤：

1. 实现 `GET /reports`：固定 environment、半开区间、时区、Campaign/Creative 版本、规则版本；最多同步查询 31 天，大查询创建导出任务。
2. 严格实现 SDD 的 CTR、点击人群 CVR、周期 CPA/ROAS、退款率；零分母、缺花费返回 null，未观察完成返回 provisional。
3. 返回来源 coverage、样本量、received_cutoff、聚合 revision、异常计数和跨期解释；保留 CTR/CVR 超过 100% 的真实结果及原因提示。
4. 落实 report_id：保存不可变报表快照/对象引用和查询参数摘要，供提案引用；不能只返回一个无法查询的随机 ID。所需元数据表作为 S1 迁移细化补充进 SDD。
5. 组合 snapshot、汇总与点击人群查询时固定同一数据截止点；修订后生成新快照，旧引用继续可追溯。
6. 导出任务校验身份归属与环境，返回带口径和 synthetic 标签的结果，复用托管运行能力，不在 HTTP 请求中生成大文件。

改动位置：`report.service.ts`、报表查询 repository、报告快照/导出适配、前后端 report types。

验收：E03、E06；100 曝光、10 点击、2 订单、1000 分费用、5000 分净收入得到 10%、20%、500 分、5；覆盖跨日/跨期、观察未结束、退款修订和不完整费用。

### CP06：效果看板、消费者页与 S1 验收

**目标：**交付可浏览、可操作、可对账的第一版业务闭环。

实施步骤：

1. 新增独立营销看板，支持环境/日期/素材版本过滤、样本量、费用覆盖和更新时间；旧 Dashboard 的 legacy 点击单独标记。
2. 接入消费者展示、曝光计时和点击跳转；用种子记录创建活动并绑定旧广告，管理页与消费者页切换明确。
3. 准备幂等演示种子及 S1 对账脚本；默认仅写专用测试数据库，拒绝非 synthetic/sandbox 数据目标。
4. 运行 E01–E07；除模型外，关键链路必须经过 HTTP、真实 MySQL 和独立 Worker，不以纯函数测试代替。
5. 浏览器验证滚动曝光、隐藏页不计时、重复点击、缺数据显示、报告过滤和刷新；构建成功不能代替这些交互检查。
6. 输出 S1 报告：数据总数、有效/隔离/重复数、归因修订、账本对账、延迟、被跳过测试和未验证部分。

改动位置：前端 `MarketingDashboard.tsx`、`MarketingConsumerPage.tsx`、`api.ts`、类型；`scripts/seed_marketing.*`、`scripts/verify_marketing_s1.*`、`docs/validation/marketing/S1.md`。

通过条件：E01–E07 全通过且精确对账，旧功能无回归；缺真实模型不阻塞 S1。完成后才能启动 S2 上线。

## 5. S2：品牌、创作者与内容生产

### CP07：品牌、商品事实、创作者与角色

- 新增 `003_marketing_content.sql`，扩展品牌需求、商品事实、创作者档案、素材授权与审核数据；S1 已建的资源表增量演进，不重复建另一套资源。
- 实现 briefs、product facts、creators 接口，版本不可变；明确事实来源、有效期、受众来源和更新时间。
- 增加运营、创作者、审核者角色；服务端统一检查品牌与素材归属，创作者仅修改自己的草稿，不能批准自己的发布请求或操作预算。
- 活动/素材状态变更在服务层检查迁移规则、版本、审核和授权；S1 手工审核记录继续可读取。
- 落点：`content-resource.service.ts`、权限 service、品牌/商品/创作者页面及接口类型。
- 验收：跨品牌访问、越权审核、过期商品事实、已发布版本覆盖均拒绝；缺目标或商品依据返回待补信息。

### CP08：图片/视频预处理与分析任务

- 使用共享素材对象引用；模型不能任意抓取客户端 URL。核对素材哈希、MIME、大小和时长，再产生分析任务。
- 图片保存原图证据；视频按 SDD 限制读取 ≤60 秒、每 5 秒抽帧并补首尾、最多 14 帧，提取音轨并转写；产物引用记录时间位置和覆盖范围。
- 模型供应商通过适配层接入，保存模型/提示词/输入版本和实际费用；分析使用独立并发额度、执行超时与取消清理。
- 复用 hosting 的任务生命周期，但分析权限不等价于任意 shell 权限；必要预处理由固定参数媒体任务执行，不允许模型生成任意命令。
- 输出 observed/product_fact/inferred、事实证据、冲突及待检查项；模型格式错误/超时保留草稿和错误信息。
- 落点：`marketing/content/media.py`、`analysis.py`、provider adapters、托管任务类型与素材证据 schema。
- 验收：C01；格式、视频长度、抽样遗漏、取消和对象存储失败可验证；真实模型尚未配置时只标记适配/模拟验证通过。

### CP09：有依据的创意生成、版本与审核

- 基于固定商品事实版本、brief、创作者资料和分析产物生成标题/正文/脚本；返回事实引用及品牌约束检查。
- 关键价格、功效、销量无 fact_id 或事实失效时阻止进入可发布状态；提示词之外增加结构和事实引用校验。
- 新稿保存新 Creative 版本；实现 pending_review、approved/rejected、archived 和授权检查。
- 现有 `/generate/creative` 保持兼容，新营销生成接口使用独立 schema；已发布素材更新不能改变历史 decision 引用。
- 落点：`marketing/content/generation.py`、`api/generation.py` 适配、审核 service、Creative 版本 repository。

### CP13：查单恢复与托管会话回执

- 复用 `GET /api/operations/:id`；网络超时保留原键和参数，查单不可用时不重发，明确不存在时才用原键重发。

- SQL 事务不包含跨服务调用；hosting 不可用时业务结果仍可查，回执稍后补发；重放不重复插入执行成功消息。
- 取消聊天只取消尚未执行的提案/任务；已经提交的出价变更以业务结果为准。
- 落点：营销 receipt outbox worker、`hosting/api.py`、`hosting/repository.py`、回执 schema 与独立故障脚本。
- 验收：A03/A04；模拟提交成功响应丢失、回执丢失、消费后崩溃和重复投递，广告不重复修改。

## 7. S4：分发策略与模拟预算

### CP15：策略快照、候选过滤与频控

- 新增 `005_marketing_delivery.sql`，创建策略版本、实验和预算基础表；分发引用不可变素材与策略版本。
- 候选按活动状态、时间、商品、审核、授权和显式受众条件过滤；通过索引有界召回，单 Campaign 活跃候选最多 200。
- 实现可解释规则排序与新素材探索；历史点击率先平滑，记录先验、权重、随机种子、候选集/截断信息与选中原因。
- 同会话/Campaign 每小时最多 3 次曝光；Redis 原子 reservation 在曝光后转已曝光计数，未曝光过期释放；重复曝光不重复转计数。
- Redis 故障时依赖频控的新分发拒绝或停用，不静默不限频；旧广告墙继续维持其独立兼容行为。
- 落点：`delivery.service.ts`、`frequency.service.ts`、policy snapshot loader、decision repository。
- 验收：C02、D01；并发展示不突破限额，候选限制有提示，同一历史输入与种子可重放选择。

### CP16：CPC 模拟预算与唯一计费

- 实现预算配置接口，限定模拟环境；固定 CNY 整数分、日/总预算、版本和 CPC 单价。
- 展示 decision 冻结单价；唯一有效点击计费时按“总预算→日预算→唯一流水”顺序锁定并扣减，同事务提交余额和流水。
- 对同 impression 建唯一模拟计费键；死锁/暂时错误仅用原键有限重试。
- 正确处理上海日界、已签名点击时间、迟到点击、余额不足和活动停止后的既有凭证；耗尽记录 unbilled_budget_exhausted。
- 实验组配额独立，组预算总和不超过 Campaign 限额；组配额的扣减与 Campaign 日/总预算共用一笔事务，冻结锁顺序。
- 模拟账本接入 CP03 coverage 机制；余额与全部有效流水对账，退款不自动恢复预算。
- 落点：`budget.service.ts`、`billing.service.ts`、ledger adapter、预算接口与多进程验证脚本。
- 验收：B01/B02；竞争扣费后总/日/组余额不负、账本一致、重复点击最多一笔费用。

### CP17：实验分组、策略回放与分发界面

- 实验按会话+experiment_id 稳定哈希分组；冻结指标、观察窗口、归因规则、比例、样本规则和停止阈值。
- 同一 Campaign 同时最多一个活动实验，创建/启动在事务中检查；分配组预算并校验 CP16 的上限。
- 实现 strategy_replay，基于历史 decision 的候选、上下文、版本和随机种子比较决策差异；未展示素材的未知效果保持未知。
- 实现策略激活接口，校验目标快照存在、版本完整和环境一致；切换、停用及降级记录时间与审计。
- 前端展示分组、策略版本、费用/预算、数据观察状态与受污染区间，synthetic 标签持续可见。
- 落点：`experiment.service.ts`、`policy.service.ts`、回放脚本、分发实验/预算组件。
- 验收：D01；刷新不改组、同输入可复现、配置不能看结果后静默修改，策略回滚有记录。

### CP18：S4 对账、容量与故障验收

- 执行 B01/B02/D01 的真实 MySQL、多进程竞争；注入 Redis、预算数据库、聚合 Worker 故障。
- 建立可重建的 1 万广告/10 万素材版本/100 万事件专用性能数据集；记录候选分布、索引、机器与连接预算。
- 按 SDD §13.2 跑事件、分发、报表独立持续负载和 AI 延迟隔离；首版不足时报告瓶颈与实际容量，不改成小数据“通过”。
- 配置聚合最老年龄、5xx、回执延迟、预算差额监控；预算差额不为 0 即失败，不能仅告警后继续给通过结论。

## 8. S5：反馈学习与策略验证

### CP19：观察窗口、反馈去重与学习

- 新增 `006_marketing_learning.sql`；每个 impression/learning_version 一个反馈状态，24 小时观察窗口。

- 复用有界批次、租约和对账机制；测试使用可注入时钟推进观察窗口，端到端至少验证真实任务领取和数据库提交。

- 验收：L01；重复点击、到期竞争、旧 Worker 和迟到反馈不造成重复或错误学习。

### CP20：学习快照发布、激活与回滚

- 每分钟发布不可变快照，包含样本 cutoff、成功/失败计数、先验、算法与模型状态版本；对象写入事务外，元数据提交时校验来源版本。
- 分发只读快照，不在请求内训练；记录用于选择的 snapshot_id 和随机种子。
- 激活经过 CP17 接口，核对对象摘要与版本；损坏/缺失快照拒绝激活，保留当前冻结策略。
- 将异常延迟、预算问题、效果停止阈值接入停用流程；切回冻结规则时记录污染区间并停止继续输出纯净实验收益。
- 落点：`marketing/learning/snapshots.py`、policy loader、激活 service 与实验状态组件。
- 验收：L01/D01；发布时崩溃、同版本重复发布、对象失效和回滚都有确定结果。

### CP21：学习实验、报告与 S5 验收

- 用固定随机种子的合成素材点击概率验证探索与恢复机制；明确这是合成验证，不等于营销效果。
- 与冻结规则做有对照实验，记录分组、样本、预算、观察时间、策略切换与预先声明的指标。
- 有真实流量时再报告真实 CTR/成本结果；无真实流量时业务收益保持“未验证”，不要求捏造提升比例。
- 学习样本数与唯一有效曝光反馈精确对账，报告未到期和迟到样本；点击优化不能写成转化/利润优化。
- 落点：`evaluation/marketing_delivery/`、实验报告生成器、`docs/validation/marketing/S5.md`。
- 通过条件：L01、快照恢复、回滚和固定集机制验证通过；真实效果验收与技术验收分别标记。
